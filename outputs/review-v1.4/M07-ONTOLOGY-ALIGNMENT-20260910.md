本轮按用户最终裁决实施：预算归属单家企业，主目录以企业为主；持仓按现有台账范围内的产品汇总；集团汇总和临时投资组合按视图/对象集处理。

实施工作区：`/Users/domi/Public/Vibecoding/ontology3.0-worktrees/prototype-composite-v1.3.0`，分支 `codex/prototype-v1.3.1-composite`。本轮读取并修改实际实施目录，没有用旧审查快照代替修复源码。实施提交：`4a1c65e9`。

## 结果

- 公司4承载企业预算演示视图，3个责任部门、6条年度预算和96条科目期间明细从企业下钻。
- 2025年企业费用预算1,097.70万元、实际费用861.7265万元，执行率约78.50%；金额沿用原预算模块，不沿用此前四张不对应的预算费用示例卡。
- 预算原来源没有指定现有21家企业中的哪一家。公司4归属属于用户授权的演示映射，页面、报告和来源记录均明确说明；不宣称原工作簿确认了真实企业隶属。
- 主目录是23个企业对象，包含原有21个风险企业及2个保留独立身份的贷前演示主体；部门和其他业务记录不与企业混排。
- 原301笔重点融资已按工作簿借据编号形成单笔对象。公司4、风电公司07、公司1分别有75、176、50笔，余额与原汇总一致。
- 集团融资总览为汇总视图，全量5218笔、574主体的口径与下方三家重点企业的下探范围分开说明。
- 投资产品分析集为对象集。4个产品、3个产品汇总持仓、208条时点观测有明确身份；没有虚构投资账户或正式组合编号。

## 复核发现的关闭情况

| 原问题 | 修正与验收 |
| --- | --- |
| MO-001：类型没有完整M01绑定 | 当前实例全部解析到V2 Object Type，属性与关系端点明确；未知类型、错误版本、候选版本和身份冲突不能通过目录构造 |
| MO-002：融资集合冒充单笔 | 集合转为对象集，301笔借据逐笔定位；公司4集合75笔可分页打开具体原借据编号 |
| MO-003：集团融资汇总包装为对象 | 主目录移除该实例，保留集团融资总览；分类属性、实体与视图区分 |
| 问数旧部门编号不能定位 | 对 `dept-equipment / dept-technology / dept-safety` 建立明确兼容映射；实际「带入探索」进入公司4，保留对应部门范围 |
| 静态快照进入模型沿用全目录时间窗口 | 从企业全景进入模型时使用对象实际截至日，避免包含其他业务日期的默认目录范围导致时间不兼容；保留原返回位置 |
| 窄屏预算表需要大量横向滚动 | 手机端改为部门预算卡片，关键数值与明细入口直接可见 |

金融机构、负责人等旧引用也保留明确的兼容身份映射；旧预算费用卡和集合入口按视图迁移，不被认作新的实体身份。候选机构关系不因此升级为借贷关系，借贷关系仍来自实际借据字段。

## 实际操作范围

使用独立4484/4482/4483服务、4486浏览器；最终回归使用全新的浏览器上下文。以下均为本轮实际操作，不引用旧通过记录作为结论：

1. 企业目录 → 公司4 → 企业预算 → 安全运行部年度预算 → 16条科目期间明细及分页。
2. 年度预算 → M01精确对象定义 → 返回同一年度记录。
3. M01对象定义 → M02来源投影 → 成员切换、分页、完整JSON下载。
4. 公司4 → 75笔融资集合 → 原借据 `DEMO-DEBT-004827`。
5. 企业预算加入原报告编辑器，核对12行指标、精确对象类型及V2引用；编辑、预览、实际下载HTML并返回企业。
6. 在原问数模块回答三个部门的2025费用预算执行情况；结果「带入探索」定位公司4与三个部门范围。
7. 公司4原融资待办 `TD-6872111633` 承接、开始、填写完成结果、确认完成、返回；新反馈可见，原融资成本和红灯保持原值。
8. 企业共同指标比较、SVG企业地图、优先显示部门关系的有界关系图。
9. 企业快照交给原M08，核对企业身份、原S003数据与语义版本、2025-12-31时点；返回原位置。
10. 集团汇总视图、投资产品分析集、产品→汇总持仓→79个实际观测日期，保存并刷新恢复。
11. 1440×900、1280×720、390×844、320×844布局及手机预算卡片。

本轮相关测试140/140通过，构建成功；保留原大包体积提示。最终浏览器回归和补充回归没有页面运行异常。
