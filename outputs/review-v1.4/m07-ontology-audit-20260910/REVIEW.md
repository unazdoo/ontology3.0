# M07 对象边界与 M01 对应关系复核

日期：2026-09-10。实施源码检查点：`329d92ff`，业务实现提交 `db8fe5c3`。本轮只读取实施源码、独立操作页面并记录证据，未修改业务源码。

## 结论

当前 M07 尚未形成由 M01 已发布对象类型完整驱动的对象目录。它组合了部分有 M01 来源的业务资源、M07 自定义类型、企业身份整合投影、聚合视图和模型候选语义引用。

这属于对象建模和消费契约的问题，不能用页面联动、办理闭环或既有测试通过替代验收。上一轮业务呈现和事项交接的验收结论，不覆盖本轮发现的本体对应关系缺口。

- 在M01打开融资已发布版本、资源与模型、所属板块属性详情；读取本轮运行时的4个已发布本体、21个Object Type。

## 发现（按严重度）

### P1 / MO-001：M07类型引用没有形成完整、可验证的M01发布绑定

复现步骤：

1. 平台进入本体管理，查看已发布本体；当前是融资、预算、债务风险、贷前调查4个本体。
2. 查看各本体的Object Type，比较M07目录的企业、预算单元、申请主体、产品、持仓和组合。
3. 核对M07的 `objectTypeId`、`canonicalObjectRef.objectTypeRef` 与具体M01对象类型ID及已发布版本。

实际：M07多使用 `m01.object-type.*`、`Enterprise`、`InvestmentProduct` 等引用；这些并非当前M01已发布对象类型的直接ID。部分融资资源具有 `sourceObjectId` 可追到定义，但主目录类型与实例身份仍未形成统一的精确映射。预算M07引用 `S002-ONTO-v1`，M01实际版本为 `SEM-S002-BUDGET-v1`，未找到二者在M07消费端的精确版本映射。

投后更明显：M07引用 `S005-SEMANTIC-CANDIDATE-v1` 展示产品、持仓、组合；M01目录显示的是「投后评价模型合同」，对象类型0类，没有对应的已发布S005对象本体。模型合同不能作为完整Object Type发布的替代证据。

源码依据：

- [M07加载逻辑](/Users/domi/Public/Vibecoding/ontology3.0-worktrees/prototype-composite-v1.3.0/designs/prototype-work/v1.4/composite/modules/m07/app.js:2034) 从静态portfolio文件和事项种子加载，未读取M01已发布类型清单。
- [M07资源校验](/Users/domi/Public/Vibecoding/ontology3.0-worktrees/prototype-composite-v1.3.0/designs/prototype-work/v1.4/composite/modules/m07/app.js:1987) 校验资源结构，未验证Object Type是否存在于对应M01版本。
- [M01组合发布入口](/Users/domi/Public/Vibecoding/ontology3.0-worktrees/prototype-composite-v1.3.0/designs/prototype-releases/v1.1.0/ontology-management-review/canvas-first/portfolio-integration.js:83) 合并S001—S004，没有S005对象发布。

用户影响：业务人员会认为当前目录是本体构建的统一成果，实际上部分类型、字段、版本和关系由不同实现分别定义；后续在M01修订并不保证M07同步使用，可能产生同名不同义或旧定义持续展示。

修正建议：先定义统一对象注册和显式消费映射，再由M07读取选定发布版本的投影。别名允许存在，但须明确解析到精确对象类型、属性、关系及身份规则；候选语义应先完成上游发布准备。

验收标准：每个进入M07的业务实例都能解析到M01对象类型、精确发布版本、数据来源、身份字段和映射；每条关系的两端类型和关系定义可核对。不能仅以名称或 `m01.` 前缀判定对应成功。无效类型在上游验收环节处理，不把资料缺失页面加入M07业务主线。

### P1 / MO-002：融资明细集合与单笔融资明细使用了不同粒度

复现：M01打开「融资明细」对象类型，身份字段为借据编号；M07打开公司4的关联业务「单位553 · 融资明细集合」。

实际：M07将75笔融资的聚合对象标为 `m01.object-type.financing-detail`，并引用 `OBJ-FINANCING-DETAIL`。M01的同源类型代表一笔借据，M07实例代表一组借据。存在定义来源并不等于实例粒度正确。

用户影响：集合可能被当成一笔融资参与关系、统计或行动，导致计数和定位不一致。

建议：原借据继续作为融资明细实例；「75笔融资」改为企业下的关联集合入口，保存集合条件和成员引用。若业务确实需要管理融资包，则另行定义有独立业务身份的融资包对象。

验收：单笔借据可按借据编号定位；集合不占用单笔实例身份，不被计为一笔融资；数量与原记录范围一致。

### P2 / MO-003：「集团融资板块」把汇总视图包装为对象

复现：M07目录选择集团融资板块；M01融资发布版本中查看Object Type与Property。

实际：M01融资版本只有融资主体、融资明细、融资机构、融资负责人4类对象。「所属板块」是 `PROP-FINANCING-ENTITY-SECTOR` 属性。M07集团融资板块的 `sourceObjectId` 为null，主要保存集团级融资汇总指标，没有对应的集团融资板块对象定义。

依据：[portfolio.json](/Users/domi/Public/Vibecoding/ontology3.0-worktrees/prototype-composite-v1.3.0/designs/prototype-work/v1.4/composite/modules/m07/resources/portfolio.json:779)、截图04与05。

建议：

- 企业所属产业/业务板块，当前按属性或受控分类维护，用于标签和筛选。
- 当前「集团融资板块」改为「集团融资总览」汇总视图/对象集入口。
- 如需管理有独立组织身份的集团，则作为组织/企业实例，使用成员关系承载集团结构；如业务板块有独立负责人、预算和生命周期，也可进一步建模为组织单元对象。两者都需要先明确业务身份与责任。

验收：目录实体、分类属性和集合视图在定义上区分；集团汇总与板块标签不共享一个含混的对象类型；删除该伪对象不丢失集团融资分析能力。

## 当前7类主目录对象的处理建议

| M07当前类型 / 数量 | 是否适合作为对象类型 | 当前对应情况 | 建议归属 |
| --- | --- | --- | --- |
| 企业 / 21 | 适合，作为统一业务主体 | M01分别有融资主体、企业财务风险事实和集团成员借款人；统一Enterprise由M07企业主数据脚本拼接，未形成统一M01类型消费绑定 | 统一企业类型与身份；融资主体、借款申请人作为角色或业务视角；财务事实另保留观测粒度 |
| 集团融资 / 1 | 当前记录适合做汇总视图 | 无对应M01类型，sourceObjectId为空 | 集团融资总览/对象集；所属板块仍是属性；真实集团组织单独建模 |
| 预算单元 / 4 | 需重新确定语义和粒度 | 「总部管理费用、信息科技费用」混合了责任范围与费用分类；M01已有预算主体、预算科目、预算版本、实际凭证等 | 科目定义用预算科目；主体+年度/期间+科目+预算版本的业务记录可定义为预算明细；不能把费用名称直接当组织主体 |
| 申请主体 / 2 | 主体适合作对象，申请人身份通常是角色 | M01已有集团成员借款人、贷款申请；M07的LoanApplicant类型没有精确绑定到其中一个 | 主体复用企业/借款人身份；有编号、金额、期限和审批状态的贷款申请独立作为对象 |
| 金融产品 / 4 | 适合 | 当前无对应M01已发布S005对象定义，M07引用候选语义 | 建立产品类型、产品代码身份及产品分类属性 |
| 投资持仓 / 3 | 适合，但必须明确身份和时点 | 当前无对应M01已发布定义，holding-01等来自展示资源 | 账户/组合与产品之间具有数量、金额、成本等属性的持仓对象；持仓与时点快照分开定义 |
| 投资组合 / 1 | 有正式管理身份时适合 | 当前主要作为持仓汇总容器，无对应M01已发布定义 | 正式组合需组合编号、账户、管理人、策略等身份与职责；临时分析选择则保存为对象集 |

下探对象也应同步核对：金融机构和负责人已有融资M01对象来源，可保留并统一实例身份；规则定义归Rule、计算指标归Metric、行动定义归Action Type。规则求值结果、报告及评估记录可以按业务需要成为有明确身份的记录类型，但不能一律把定义本身或页面容器写成Object。

## 对「所有对象都在本体模块作为object维护」的准确解释

M01应统一维护对象类型、属性、关系、指标、规则、行动和来源映射。企业这个类型维护一次；21家具体企业是实例，由数据源通过身份和映射形成，在M07面向业务使用。无需为每家企业建立一个新Object Type。

M01中可发布很多与业务建模有关的资源，但并非每项资源都属于Object：板块属性属于Property，归属关系属于Link Type，融资成本属于Metric，成本偏高属于Rule，融资优化建议属于Action Type。

M07也不必把M01的所有Object Type都铺在首页。可以优先展示企业、贷款申请、产品等主对象，其余业务记录按关系下探；展示层级由业务任务决定，类型身份由M01统一决定。

## 推荐调整顺序

1. 先定主对象、分类属性、业务记录和对象集边界，确认预算明细、持仓、贷款申请等粒度。
2. 整理一份可机器校验的M01—M07映射表，明确类型ID、实例身份、数据映射、版本、关系端点与适用行动。
3. 在M01补齐统一企业和投后定义，修正其他类型的映射；从已发布版本生成M07业务目录，减少各模块各写一套类型字典。
4. 把集团融资、融资明细集合和临时组合改为汇总/集合视图，保留业务分析入口。
5. 验收M01修订发布、M07消费版本、对象下探、原规则/行动/报告交接的一整条路径。技术准备与映射校验留在上游，M07继续呈现业务相关内容。
